# Z8 自定义快门声 (Nikon Z8 Custom Shutter Sound)

通过修改固件中的音频资源与三个长度/地址常量，把尼康 Z8 的电子快门音替换成任意自定义音频。

> **免责声明**：本项目只包含**分析与工具**，不包含任何尼康固件、固件派生数据或音频素材。
> 刷机有风险（变砖、失去保修），一切后果自负。本项目与尼康公司无关。

---

## 效果

| 场景 | 结果 |
|---|---|
| 快快门（≥1/50） | 完整播放 **340 ms** 自定义音频 |
| 慢快门（例如 1/30） | 约 195 ms（前帘被后帘打断 + 后段接续） |
| 2 秒长曝光 | 前段 340 ms + 约 140 ms 尾巴（**已知问题**，见 [未解决问题](docs/open-questions.md)） |
| C30 高速连拍 | 走独立 kind，保持原厂行为 |
| 其它音色（A/B/D/E） | 保持原厂（未被修改） |

已验证可叠加在 **ProRes + HE★ 预拍摄** 的发布版之上（见第 4 节）。

---

## 1. 这是怎么做到的

Z8 的快门音**不是文件**，而是固化在固件 EG 模块里的裸 PCM：

```
EG 虚拟地址   0x43FB8000 – 0x44009480
格式          48 kHz / 立体声 / 16-bit（左右声道几乎相同 = 双单声道）
```

固件按 **kind**（音色资源编号）索引这些音频，每个音色由 4 个资源组成：

| 类型 | kind | 合成段 | 前段 | 中段 | 终段 |
|---|---|---|---|---|---|
| A | 0,1,2,6 | `0x43FB8010` (9600B) | `0x43FBA590` (4800B) | — | — |
| B | 10–13 | `0x43FBB850` | `0x43FC28D0` | `0x43FC4E50` | `0x43FC9950` |
| **C** | **14–17** | **`0x43FCB750`** | **`0x43FD27D0`** | **`0x43FD4D50`** | **`0x43FD9850`** |
| D | 18–21 | `0x43FDB650` | `0x43FE26D0` | `0x43FE4C50` | `0x43FE9750` |
| E | 22–25 | `0x43FEB550` | `0x43FF25D0` | `0x43FF4B50` | `0x43FF9650` |

每个类型 4 个资源 = 28800 + 9600 + 19200 + 7680 = **65,280 字节 = 340 ms**，
并且这 4 个资源在 **ROM 和 RAM 里都是连续的**——这是能延长播放长度的关键。

完整的逆向分析（跳转表、分发器、初始化复制循环、播放 API、属性 ID）见
**[docs/mechanism.md](docs/mechanism.md)**。

## 2. 最小改动清单

把任意一种音色换成自定义音频，只需 4 处改动：

| # | 位置 | 原值 | 改为 | 作用 |
|---|---|---|---|---|
| 1 | `0x40E34920` | `mov w0,#0x7080` (28800) | `mov w0,#0xFF00` (65280) | 播放长度 150ms → 340ms |
| 2 | `0x43FB7EE0` | `0x40E34934` | `0x40E34920` | 慢门前帘也用 340ms |
| 3 | `0x40E34804` | `0x0A15C32180` | `0x0A15C2B100` | 前帘从块首读取 |
| 4 | `0x43FCB750` | 原厂音频 | 自定义 PCM (65,280 B) | 换声音 |

加上版本号与 CRC 更新，总共 **7 处字节差异**。

脚本见 **[scripts/](scripts/)**。

---

## 3. 音频处理流程

```
用户 WAV  →  重采样到 48 kHz 立体声 16-bit
          →  裁剪/压缩到 340 ms
          →  尾部 20 ms 线性渐隐（防爆音）
          →  峰值归一化到 -1.5 dBFS（防削波）
          →  写入 0x43FCB750 起 65,280 字节
```

## 5. 实验记录

我们一共刷了 15 个版本才把机制摸清楚（其中包括 3 次失败：死机、音频重复、长度溢出）。
完整的数据、录音分析与结论见 **[docs/experiments.md](docs/experiments.md)**。

几个关键教训：

- **长度字段是 u16、单位 4 字节**：设成 0 会回绕成 65535 单位 = 262,140 B = **1365 ms** 垃圾音频
- **播放不是整段**：短曝光下前帘会被后帘事件打断
- **慢门是分两次快门事件播的**，中间有真实快门间隔

## 6. 未解决的问题

这一节是**诚实清单**——下面这些我们没搞定或不完全明白，欢迎指正：

1. **2 秒长曝光的尾巴**：前帘播完后，后帘还会再播 140 ms
2. **1/30 的 195ms 到底怎么算出来的**：前帘是否被切断、切断点在哪，证据不完全自洽
3. **两次实验的"快门速度 ↔ 播放窗口"结论相反**，未能重现
4. **约 50ms 的固定偏移**：是 DMA 启动丢弃还是播放器自带偏移，未确认
5. **cap 裁切机制**：`min(资源长, cap×192)` 里的 cap 从哪来、C 型的 cap 是多少
6. **能否超过 340ms / 65,280 字节**：受 RAM 缓冲区限制，未尝试扩容
7. **C15/C30/C60/C120 的阶段分派**：只知道 C30 走独立 kind（kind6 循环）
8. **Z30 式的 SD 卡 WAV 播放**：完全没做

详见 **[docs/open-questions.md](docs/open-questions.md)**。
