## Q1. 2 秒长曝光的"多余尾巴"

**现象**：2 秒慢门时，前帘完整播完 340 ms，2 秒后**后帘又播 140 ms**。

**为什么难**：1/30 和 2 秒用的是**同一个后帘**（kind16/17）。
1/30 下后帘是必要的（你听到的 195 ms 里有 140 ms 来自它）；
2 秒下它就成了多余的尾巴。

**已排除**：纯数据改动无法区分——后帘触发时固件里没有"前帘是否播完"的状态。

**可能的解法**：找到"选择慢路径"的那个判断（据说受实际 Tv 门控），
在旁边加一个阈值比较：Tv 慢于某值时后帘改用静音 kind。
**但我们还没定位到那段代码。**

## Q2. 1/30 的 195 ms 到底怎么算出来的

**实测**：1/30 总长约 195 ms。
**推算**：前帘（33 ms 被打断）+ 后帘 100 ms + 40 ms = 173 ms，**对不上**。

**矛盾点**：
- 如果把 kind15 的长度从 9600（50 ms）改成 65280（340 ms），
  1/30 的总长**没有变化**——说明 kind15 可能根本不是前帘实际使用的资源；
- 但 2 秒曝光时，前段确实播了 350 ms（≈ 改后的长度）——说明它**又**生效了。

**未解释**：两条观测互相矛盾，中间缺一环。

| 实验 | 1/30 用 | 1/1000 用 |

| 扫频（04.25） | 窗口 A（~48 ms 起） | 窗口 B（~196 ms 起） |

两次都确认跨槽、起点也都对得上（都有约 50 ms 的偏移），唯独**分配反了**。

**猜想**（都未验证）：

- 或者存在我们没意识到的状态依赖。

S3 的经验是"没有观察到随机反转"。

## Q4. 约 50 ms 的固定偏移

**现象**：两次实验中，可听声音的起点都比预期晚约 48–53 ms（≈ 9600 字节）。

**两种可能**：
1. **DMA 启动丢弃**：音频引擎前 50 ms 的数据没送到扬声器；
2. **播放器自带偏移**：本来就从样本内 +50 ms 处开始读。

**为什么重要**：如果是 1，自定义音的前 50 ms 会被吃掉，需要前置静音补偿；
如果是 2，则不需要。

**判断方法**（未做）：把自定义音的前 50 ms 填成明显的标记音，看是否被吞掉。

## Q5. cap 裁切机制

S3 提供的资料提到：

> cap 非零时最多提交 `min(资源长, cap × 192)` 字节；延长资源不能自动绕过 cap 66。

`cap × 192` 的单位和 192 字节/毫秒吻合，所以 cap 可能是"毫秒数"。

**未知**：
- cap 存在哪个结构里？
- 普通拍摄（S 单张）的 cap 是多少？是否为零（不裁切）？
- C15/C30 等模式各自的 cap 是多少？

**为什么重要**：如果普通拍摄也有 cap，我们把长度改到 340 ms 可能只是"没被裁到"，
换个模式就会失效。

## Q6. 能否超过 340 ms / 65,280 字节

**当前限制**：C 型的 4 个资源总共 65,280 字节，ROM 和 RAM 都只有这么多。

**引擎上限**：65,535 × 4 ≈ 1.37 秒（u16 长度字段）。

**可能的扩展方式**（均未尝试）：
1. 借用相邻类型（C/D/E 在 ROM 和 RAM 里连续，牺牲 D/E 可到约 1.0 秒）；
2. 找空闲 RAM 重新指定复制目标；
3. 走 Z30/mark2 的独立 PCM 缓冲路线（Z9 侧做到 1.5 秒）。

**风险**：改动越大越容易死机（04.29 就是教训）。

## Q7. C15 / C30 / C60 / C120 的阶段分派

**已知**（来自 S3 提供的 Z9 资料）：
- C15 用 `kind0 / repeat0 / cap 0x42(66)`
- C30/C60/C120 用 `kind6 / repeat0` 循环
- C15 循环节奏约 66 ms，后三档约 40 ms

**实测**：我们改的 kind14–17 对 C30 **没有影响**（C30 保持原厂声音）。

**未知**：Z8 上这四档各自用哪些 kind、是否也有 cap、如何逐档自定义。

## Q8. Z30 式的 SD 卡 WAV 播放

Z30 的实现是"hook 原厂音频队列 + 从 SD 读 WAV"，
能做到 1.08 秒、用户随时换文件。**我们完全没做。**

**需要的组件**（部分已有）：
| 组件 | 状态 |
|---|---|
| 快门触发点 | 知道事件码 `0x04190001`，未定位代码 |
| 音频注入点 | 知道播放 API `0x40E31A44`，未确定能否喂自定义缓冲 |
| SD 文件 API | ✅ 已有（在预拍摄补丁的工具链里） |
| 菜单框架 | ❌ Z8 与 Z30 完全不同，工作量最大 |

**最小可行版本**：不做菜单，固定读 SD 根目录的 `SHUTTER.WAV`。

## Q9. 播放窗口的长度是表还是常量

我们改的是"长度 getter 返回的常量"。但**播放窗口本身**（135–150 ms）
是不是另有来源？

**证据**：把 kind14 的长度从 28800 改到 65280 后，实际播放从 150 ms 变成了 340 ms
——说明**长度 getter 就是唯一的长度来源**（对我们改的这条路径而言）。

但扫频实验测出的"窗口约 140 ms"和"长度 150 ms"很接近，
可能是因为扫频实验时长度还没改。

**已基本确认，但保留疑问。**
